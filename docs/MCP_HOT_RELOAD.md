# Per-source MCP hot reload (operator guide)

**Status:** experimental, opt-in through a staged build. This document describes
source behavior, not a deployed feature. Do not replace an active Codexify
service without separate approval and validation.

## Scope

`reload_mcp` reloads exactly one existing upstream source. Its `source`
argument must match the **exact configured MCP server key** from the resolved
`mcpServers` configuration (including inherited Codex MCP sources). For example,
if the configured key is `god-prompt-mcp`, call
`{"source":"god-prompt-mcp"}`. Do not substitute a normalized catalog source ID
such as `god_prompt_mcp` from `mcp_list_sources`: it is not necessarily the
configuration key and can return `SOURCE_UNKNOWN` without changing the running
connection. The call cannot supply a command, executable, working directory,
URL, environment variables, or credentials.

The server rereads its operator configuration (including inherited Codex MCP
sources) **read-only** using its startup CLI selection. A target that was
removed or disabled fails closed. No global service restart, tunnel reconnect,
task replacement, or unrelated source reconnection is part of this operation.

The replacement uses the existing MCP transport implementation for **stdio**
and **Streamable HTTP**. Unsupported legacy SSE and WebSocket sources remain
unsupported; the operation never silently falls back to a process-wide restart.

## Lifecycle and safety

1. The scoped reload lock rejects concurrent attempts for the same source
   (`RELOAD_IN_PROGRESS`); unrelated source reloads can progress concurrently.
2. The updated source specification is validated, started, initialized, and
   queried with `tools/list`. A bounded MCP ping must also receive a
   successful response or a protocol-level MCP error indicating a live peer.
3. The new tool definitions are validated and an immutable registry view is
   constructed. The new view replaces the old view in one atomic pointer swap.
   Concurrent distinct-source reloads rebuild against the latest view.
4. Each dispatch retains only its selected validated upstream tool and that
   source's connection generation. Write-capable calls are **never replayed**;
   unrelated direct/gateway sources are not retained by a long-running call.
   Cancellation and timeout semantics remain those of the forwarded request.
5. The old generation is released when no selected old tool or catalog
   snapshot retains it. The operation reports whether forwarded calls drained
   within the source's configured `requestLimits.slowCancellationMs` interval.
   The separate `oldGenerationStillReferenced` flag covers retained references
   even when no forwarded calls remain. A drain timeout does **not** kill or
   replay an in-progress side-effecting call.
6. On failure **before** the swap, the new candidate is dropped and the old
   view is never replaced. Errors use bounded diagnostic codes and do not
   echo credentials, command lines, headers, environment variables, or raw
   tool-response bodies.

For stdio, the spawned Tokio child has `kill_on_drop` enabled, so aborted
initializations should not leave the candidate running. A platform-specific
Windows child-lifecycle integration and repeated process-tree soak remain
required acceptance gates before production activation.

## Result and tool discovery

A successful result includes `source`, `outcome`,
`previousGeneration`, `replacementGeneration`, old/new reported MCP
server versions, readiness, counts of added/removed/changed/unchanged
tool definitions, `oldCallsDrained`, `oldCallsStillRunning`,
`oldGenerationStillReferenced`, `oldGenerationRetiring`, `rollback`,
`diagnosticCode`, and measured
`timingsMs` for initialization/readiness, registry switch, draining and total
reload duration.

The source's discovery data and forwarded-call routes change together in the
server's tool registry. Existing transport sessions can observe changed
definitions on **another `tools/list`** request. **An already-open ChatGPT
chat is not guaranteed to receive new tool definitions automatically.**
Its connector may need Refresh, reconnection or a new conversation before
new direct tools appear. The result explicitly sets
`clientRediscoveryRequired: true`.

Catalog-mode source and tool identifiers remain generated by the existing
catalog and may change when a source's tool set changes. Re-query
`mcp_list_sources`, `mcp_search_tools`, and `mcp_get_tool` before calling
a new or modified tool. Gateway clients must refresh their advertised schema
and generated skill after reload.

## Failure and boundary conditions

- `SOURCE_UNKNOWN` / `SOURCE_REMOVED` / `SOURCE_DISABLED`: verify the
  exact configured MCP key, not a normalized catalog ID. Do not spawn an
  arbitrary process or reinterpret the input as a path.
- `RELOAD_IN_PROGRESS`: no duplicate replacement of the same source.
- `CONFIG_INVALID`, `CONFIG_CLI_INVALID`, `INITIALIZE_FAILED`,
  `READINESS_FAILED`: old healthy generation is retained.
- `TOOL_NAME_LIMIT`: bound on unique registered direct/gateway tool names;
  the attempted registry swap is discarded.
- `CANCELLED`: an aborted preparation does not switch generations.
- If the old generation became unhealthy independently, a successful new
  connection is preferred; the operation does not imply that the old peer can
  be resurrected.
- Resource links issued before a reload are separate capabilities. An upstream
  resource fetched **after** its old connection retires can fail; request a
  fresh resource link from the new source. Already-running resource reads
  retain their own peer and cancellation semantics, but cross-generation
  resource-link durability is not claimed by this implementation.
- Invalid data from upstream tool descriptions must remain untrusted.
  Reload permission uses existing Codexify connector authorization and audit
  boundaries. Do not expose the control plane to unauthenticated clients.

## Verification gate

The following must pass on the **exact candidate commit** before any
deployment: Rust formatting and compilation, strict lint, full Rust suite,
downstream HTTP MCP handshake, selected-source version and tool-diff checks,
two independent unrelated MCP sources, read/write in-flight calls, duplicate
reload and failure injection, cleanup/leak soak, and Windows native-process
termination. Reproduce an isolated old-to-new GodPrompt candidate switch
without touching the running GodPrompt instance; verify new version and
rollback. Measure switchover, drain and end-to-end request latency using a
repeatable workload. Do not report "zero downtime" without observed proof.

**Not included:** automatic filesystem watching. It remains disabled rather
than introducing unverified debouncing and partially written config races.

This feature does not merge the separate Windows scheduled-supervisor orphan
cleanup branch. Keep that work independent and verify its eventual integration
before any production cutover.

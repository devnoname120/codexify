# Self-update changelog and progress widget design

## Goal

Make `self_update` show the verified release changelog and render an in-conversation MCP App that monitors the detached executable replacement through service restart, without exposing its polling primitive to the model.

## User-visible behavior

`self_update` keeps its explicit `confirm=true` authorization boundary. Its synchronous preflight still downloads, verifies, extracts, and probes the release before returning. The returned card shows the source and target versions, the relevant changelog sections, and a progress state for the detached phase.

For service-supervised updates, the card polls while the connector is available, tolerates the expected transport outage during restart, and resumes polling when the host reconnects it. A terminal state is shown only when Codexify's durable updater record proves success, rollback, or failure. If no terminal record can be observed within 60 seconds, the card says that completion could not be verified and offers a manual retry; it does not falsely claim failure.

A successful card retains the instruction to refresh the Codexify connector in ChatGPT Settings so the host reloads the updated tool catalogue.

Foreground Unix updates are represented honestly: the installed binary can be replaced, but the already-running process remains the previous version. The durable worker state can still report a successful replacement; `runningVersion` reports the responding process version separately.

## Release and changelog source

Every release archive contains `CHANGELOG.md` next to the executable. The updater extracts both from the already checksum-verified archive. It selects complete changelog sections whose semantic versions satisfy:

```text
currentVersion < sectionVersion <= targetVersion
```

This supports skipped releases. The selected text is bounded and placed in component-only result metadata, not model-visible `structuredContent`. The widget renders it as escaped plain text with lightweight heading/list formatting; it never injects release text as HTML.

If an older or malformed release archive lacks a usable changelog, the executable update remains available and the card reports that release notes were unavailable. Changelog failure is not allowed to weaken archive verification or executable validation.

## Durable updater protocol

Updater state is stored under:

```text
~/.codexify/update/status/<update-id>.json
```

The directory and files are private to the user. State writes use a same-directory temporary file followed by atomic replacement. Records are retained after the worker removes its lock and staging files so a restarted Codexify process can answer status queries.

The record schema is:

```json
{
  "updateId": "96-bit opaque identifier",
  "fromVersion": "1.1.0",
  "targetVersion": "1.2.0",
  "state": "scheduled",
  "updatedAt": "2026-08-31T12:34:56Z",
  "failureCode": null,
  "failureDetail": null
}
```

Allowed states are `scheduled`, `installing`, `validating`, `restarting`, `succeeded`, `failed`, and `rolled_back`.

Worker scripts update the record at transition boundaries. Failure details are bounded, normalized phrases generated by Codexify rather than arbitrary command output. If replacement fails and restoration succeeds, the terminal state is `rolled_back`; if restoration cannot be proven, it is `failed`. A service restart failure after a valid replacement is `failed`, because the connector is not operational even though the binary changed.

Status records are bounded in count. Creation opportunistically removes the oldest records beyond 32 retained entries. The active update record is never removed by that cleanup.

## App-only status tool

A native `self_update_status` tool accepts only `updateId`. It is project-independent and classified read-only, non-destructive, idempotent, and closed-world. Its tool metadata sets:

```json
{
  "ui": {
    "visibility": ["app"]
  },
  "openai/visibility": "private",
  "openai/widgetAccessible": true
}
```

The standard visibility prevents the tool from entering the model's available tool set in compliant hosts; the OpenAI compatibility keys preserve existing ChatGPT component behavior.

The result includes the durable record plus `runningVersion`, which is always the version of the process answering the poll. Unknown, malformed, or expired identifiers return a bounded tool error without exposing filesystem paths.

## MCP App

`self_update` links to `ui://codexify/self-update/v1/mcp-app.html`. Its result metadata contains the receipt and selected changelog. The resource uses `text/html;profile=mcp-app`, requests no external network origins, and prefers no extra host border.

The embedded app implements the MCP Apps handshake and calls `self_update_status` through `tools/call`. It polls immediately, then every second while reachable. After tool-call transport errors it backs off to two seconds. The absolute deadline is 60 seconds from the first scheduled-state render, stored in private widget state so an iframe remount does not reset the timeout. Terminal status and manual retry state are also persisted.

The card uses an accessible live status region, a compact state indicator, elapsed time, a collapsible changelog, and a manual `Check again` action after timeout or a transient polling error. It reports its size through the standard MCP Apps notification.

## Server integration

The server advertises both the existing diff resource and the update resource under the existing MCP Apps extension capability. Resource reads dispatch to either UI module after bridged and exported-file capabilities are checked.

The updater tool keeps a small structured receipt for model reasoning and puts the larger changelog in result metadata. The app-only status tool is registered normally because MCP Apps invocation still uses MCP `tools/call`; visibility metadata, rather than a separate private transport, controls model access.

## Compatibility and failure handling

Older ChatGPT hosts that ignore MCP Apps metadata still receive the textual `self_update` result. Hosts that render the card but cannot rebind its tool-call bridge across restart reach the honest timeout state and can retry after the connector becomes reachable.

The detached worker waits 10 seconds before service interruption, increasing the chance that ChatGPT has fetched and initialized the UI resource without making update completion depend on widget acknowledgement.

The status protocol is additive. Existing update locks, logs, rollback copies, service supervision, and foreground-update semantics remain intact.

## Verification

Tests cover changelog section selection, archive extraction, private atomic status persistence, record cleanup, status-tool schema and app-only metadata, self-update component metadata, widget protocol strings and safe rendering, Unix and Windows worker transitions, server resource advertisement, registry counts, and release archive contents. Full Rust formatting, Clippy, and tests run with isolated user configuration to avoid reading the developer's real `~/.codexify` state.

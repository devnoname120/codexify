# Native Host-File Ingress for Codexify

**Date:** 2026-08-24
**Status:** Implemented
**Stack:** Rust, RMCP, reqwest, cap-std
**Applies to:** codexify v1.2.0+

## Goal

Let a ChatGPT conversation materialize one user-attached or ChatGPT-generated file as exact bytes inside the active Codexify project or managed worktree:

```text
ChatGPT native file value
        │
        ▼
provider-specific validation and streaming
        │
        ▼
capability-confined, atomic workspace publication
        │
        ▼
ordinary project file + integrity receipt
```

This closes the gap between a file that exists in ChatGPT-hosted storage and a file that local compilers, test runners, parsers, image tools, or applications can open. `write_file` remains the right primitive for text generated by the model; it is not a reliable binary-transfer mechanism.

## Source of Truth

The public tool contract follows OpenAI's current plugin reference, read on 2026-08-24:

- <https://developers.openai.com/plugins/reference#define-file-inputs>
- `_meta["openai/fileParams"]` lists top-level native-file parameters.
- Each file schema declares `download_url`, `file_id`, `mime_type`, and `file_name`.
- Only `download_url` and `file_id` are required.
- Runtime field names are snake case.

The workspace confinement layer uses `cap-std` 4.0.3 or newer. Version 4.0.3 is the first fixed 4.x release for GHSA-hp8f-xmx4-4qrg; older 4.x releases must not be selected.

## Non-goals

- Arbitrary URL downloading.
- Reading arbitrary local source paths outside the active project.
- Archive extraction, execution, or MIME-based trust decisions.
- A persistent artifact database, catalogue, TTL, or retention service.
- Exporting local project files back to ChatGPT.
- A generic provider adapter registry before a second concrete source exists.
- Automatic import immediately after upload; the agent must call the tool explicitly.

## Public Tool Contract

The tool is named `import_host_file`.

```json
{
  "file": {
    "download_url": "https://...",
    "file_id": "file_...",
    "mime_type": "application/pdf",
    "file_name": "input.pdf"
  },
  "path": "fixtures/input.pdf"
}
```

`path` is required and relative to the active project root. The destination must not exist. One file is imported per call so each write has an unambiguous destination, result, size limit, and failure boundary.

The tool descriptor includes:

```json
{
  "_meta": {
    "openai/fileParams": ["file"]
  },
  "annotations": {
    "readOnlyHint": false,
    "destructiveHint": false,
    "idempotentHint": false,
    "openWorldHint": true
  }
}
```

The successful structured result is:

```json
{
  "path": "fixtures/input.pdf",
  "bytes": 183742,
  "sha256": "sha256:...",
  "source": "openai_file",
  "mimeType": "application/pdf"
}
```

`mimeType` is optional and informational. The result never includes the temporary download URL or file ID.

## Configuration

```json
{
  "artifactIngress": {
    "enabled": true,
    "maxFileBytes": 104857600,
    "requestTimeoutMs": 120000,
    "idleTimeoutMs": 30000,
    "maxRedirects": 3,
    "maxConcurrentDownloads": 2
  }
}
```

Defaults:

| Key | Default | Rule |
|---|---:|---|
| `enabled` | `true` | When false, omit the tool from `tools/list` |
| `maxFileBytes` | 104857600 | Must be positive |
| `requestTimeoutMs` | 120000 | Whole import deadline; must be positive |
| `idleTimeoutMs` | 30000 | Maximum wait between response chunks; must be positive and no greater than the request timeout |
| `maxRedirects` | 3 | Range 0-10 |
| `maxConcurrentDownloads` | 2 | Range 1-16 per server process |

The trusted provider-host policy is deliberately not configurable. Adding arbitrary hosts to a file-ingress allowlist would turn an operator typo or copied configuration into a general network-to-filesystem primitive.

## Architecture

### 1. Generic tool metadata plumbing

Extend the internal `Tool` trait with defaulted methods for:

- human-readable title;
- MCP `ToolAnnotations`;
- protocol `_meta`.

`server.rs` passes those fields through generically when constructing RMCP tool descriptors. The file tool does not receive a name-based special case in the server.

### 2. OpenAI file resolver

`artifact_ingress/openai_file.rs` owns the provider contract:

- strict deserialization of the four documented fields;
- bounded validation of file IDs and optional metadata;
- HTTPS-only URL validation;
- no username, password, fragment, or non-default port;
- acceptance only of the OpenAI-owned `oaiusercontent.com` domain and its subdomains; legacy Azure Blob hostnames are rejected because a registrable storage-account prefix is not proof of provider ownership;
- manual redirect handling with the same validation applied to every target;
- no cookies, ambient authorization headers, caller-supplied headers, or environment proxy;
- `Accept-Encoding: identity` so byte accounting is unambiguous;
- an early `Content-Length` check plus an authoritative streamed-byte limit;
- a complete-response check when `Content-Length` is present.

The signed URL is treated as a bearer capability. It is never returned or persisted. RMCP can include complete protocol messages in debug events and malformed-session errors, so Codexify applies a non-overridable logging guard that excludes every `rmcp` target; `RUST_LOG` cannot expose native-file arguments before the handler receives them.

The HTTP layer is represented by a narrow internal test seam rather than a provider registry. Production uses reqwest; tests provide deterministic status, redirect, header, chunk, error, and stall sequences.

### 3. Workspace file publisher

`artifact_ingress/workspace_publish.rs` owns destination safety independently of the source provider:

1. Reject empty, absolute, parent-traversing, directory-only, and NUL-containing destination paths.
2. Preserve both the configured project-root path and its resolved directory identity, then open the resolved root as a `cap_std::fs::Dir` using ambient authority only at that boundary.
3. Resolve and create parent directories through the capability handle, so `..`, absolute paths, symlink escapes, and concurrent path replacement cannot escape the project.
4. Create a randomly named private partial file in the final destination directory with exclusive creation.
5. Stream bytes into that file while hashing and enforcing the actual byte limit.
6. Flush and sync the completed file, then verify the written size.
7. Re-resolve the originally configured project path and verify both its canonical target and directory identity before publication, so a moved, replaced, or retargeted project root fails closed.
8. Move synchronous capability and filesystem operations to deadline-aware blocking tasks. A cancellation flag is checked immediately before and after the atomic link so work that resumes after a timeout cannot leave a published destination.
9. Publish atomically and without overwrite by creating a hard link from the partial to the requested final name, then open the destination without following links and verify that its regular-file identity and size match the still-open verified source inode.
10. Remove the partial link after publication. Failure or cancellation schedules cleanup away from the Tokio reactor.

The hard-link publication step is intentionally strict. If the underlying filesystem cannot provide an atomic no-overwrite hard link, the operation fails safely instead of exposing a partially written final path or silently replacing an existing file.

Internal symlinks that remain inside the project may resolve. Any symlink resolution that would leave the project is rejected by the capability layer. An existing final file or symlink is never replaced.

### 4. Orchestration

`artifact_ingress/mod.rs` combines the provider resolver and workspace publisher:

- acquire one bounded concurrency permit;
- open the provider stream;
- create the pending destination;
- stream, hash, and enforce limits under the whole-call deadline;
- observe the MCP request cancellation token at the queue, network, write, synchronization, and publication boundaries;
- publish and return the integrity receipt.

The file becomes an ordinary project file after publication. Git, `show_diff`, `glob`, `tree`, and other filesystem tools remain the catalogue and lifecycle mechanisms.

## Failure Semantics

Errors have stable categories and safe messages. They may include a destination path and HTTP status, but never the signed URL, query string, file ID, raw host file value, response body, or downloaded bytes.

Representative categories:

- `invalid_file_reference`
- `untrusted_file_url`
- `file_download_failed`
- `file_redirect_invalid`
- `file_too_large`
- `file_stream_timed_out`
- `file_size_mismatch`
- `destination_invalid`
- `destination_exists`
- `destination_unsafe`
- `publication_unsupported`
- `write_failed`

MIME type and filename are untrusted hints. A mismatch never grants extra behavior; the tool does not extract, execute, render, or open the file.

## Audit Policy

Normal tool logging remains limited to tool name and success/error. Any future detailed audit event may record:

- destination path;
- validated provider identifier;
- validated hostname only;
- bytes written;
- SHA-256;
- duration;
- error category.

It must not record the URL, query string, file ID, native file object, or bytes.

## Testing Strategy

### Provider and network policy

- exact OpenAI schema and `_meta["openai/fileParams"]`;
- accepted `oaiusercontent.com` apex and subdomain hosts;
- rejected HTTP, credentials, fragments, ports, arbitrary Azure hosts, lookalikes, IP literals, and subdomain tricks;
- relative and absolute redirects;
- redirect to an untrusted host;
- redirect limit;
- non-200 responses;
- declared oversize;
- streamed oversize;
- length mismatch;
- chunk error and idle stall;
- no signed URL or file ID in errors.

### Destination publication

- nested-directory creation;
- traversal and absolute-path rejection;
- symlink escape rejection;
- final-file and final-symlink no-overwrite behavior;
- destination absent until publication;
- exact bytes and SHA-256;
- partial cleanup after source error, size failure, timeout, and cancellation;
- MCP cancellation while queued and while a response body is stalled;
- atomic winner under concurrent imports to the same destination;
- project-root rename and replacement races, including a replacement symlink to the same moved directory;
- common macOS/Linux behavior, with Windows compilation covered by CI when available.

### Integration

- registry count and conditional omission when disabled;
- tool descriptor title, annotations, schema, metadata, and output schema;
- successful tool result using a fake provider stream;
- existing tools remain unchanged.

## Alternatives Rejected

### Generic `ArtifactResolver` registry now

Rejected until a second real source exists. An OpenAI signed URL, an opaque connector handle, and MCP `resources/read` have different authority, transport, retry, and error semantics. The reusable abstraction worth committing to now is the destination publisher.

### Raw local path input

Rejected. A path outside the project expands filesystem authority; a path already inside the project needs no import.

### Arbitrary URL input

Rejected. It creates SSRF, private-network access, credential-bearing URL, redirect, and exfiltration risks unrelated to native host-file transfer.

### Direct write to the final path

Rejected. Although exclusive creation prevents overwrite, readers and local tools could observe an incomplete file. Verified partial plus atomic publication gives a clean visibility boundary.

### Persistent artifact records

Rejected. Once published, the artifact is an ordinary project file. A second database would duplicate state and create lifecycle inconsistencies.
